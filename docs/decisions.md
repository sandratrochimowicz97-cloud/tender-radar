# Decisions

Newest first. Each entry: what was decided, why, and what was rejected.

| Date | Decision | Why | Rejected |
|---|---|---|---|
| 2026-11-05 | Read-only MCP server that reads only a database view of public tender facts (`public_tenders`), through its own login `mcp_reader` with no other rights | Claude can answer questions about tenders without ever seeing the practice's references, facts, Why text or decisions; the database enforces the limit, so a bug in the server can't widen it | The project's own database user (sees everything); a second, stripped Excel file (needs its own update step and goes stale); letting the model write SQL |
| 2026-11-05 | MCP server libraries: `@modelcontextprotocol/sdk` 1.32.1, `pg` 8.23.1, `zod` 4.6.5, exact versions, each released at least two weeks before adoption, no install scripts | All three are MIT-licensed ([sdk](https://www.npmjs.com/package/@modelcontextprotocol/sdk), [pg](https://www.npmjs.com/package/pg), [zod](https://www.npmjs.com/package/zod)); the SDK is the official TypeScript SDK of the Model Context Protocol project. Node is already required for n8n | Newest versions on release day; Python (a second runtime to install) |
| 2026-11-04 | The Why holds only what decides the verdict, in full; other qualifications go to a separate "Also required" column; standard paperwork (register extracts, tax and social security proof, insurance certificates, self-declarations, exclusion grounds, minimum wage and sanctions declarations) is left out at extraction | In the first full run most "Check" items were paperwork every registered firm has, and a cap of 2 items hid the rest; the reader could not see what mattered | Capping the Why at 2 items with "+N more" (hides requirements); listing all paperwork (noise) |
| 2026-11-04 | Minimums in DKK, SEK or NOK are converted to euros with fixed approximate rates in the Settings step; other currencies are left for the person to check. A rules version in Settings makes every open tender be assessed again when the rules change | The practice bids in Scandinavia, so minimums often are not in euros. Re-assessing 180 tenders costs about $0.25, so a rule change should not leave old verdicts behind | Live exchange rates (another dependency for a borderline case); resetting verdicts by hand |
| 2026-11-04 | v1 has one model step: requirement extraction. No separate relevance judge (replaces the 2026-10-25 relevance-judge entry) | The fetch step's main-CPV filter already keeps architecture and landscape notices only, so a second model call would add cost and a failure point. A relevance step is added only if the daily list shows too many irrelevant notices | A relevance judge on every notice |
| 2026-11-04 | The model only fills a fixed JSON schema (turnover, insurance, staff, lead experience, references, price weight, other requirements), each with a quote. Code drops any value whose quote is not in the notice text, then compares with the practice's facts and references | Every claim can be checked against the notice. The practice's own data never goes to the model. Verdict rules: any requirement not met = no-go; references partly met = conditional; go only for a typology the practice pursues, with every comparable minimum met and no requirement with an amount left unchecked; everything else = unresolved | Letting the model decide go/no-go |
| 2026-11-04 | Requirement extraction uses the Anthropic Messages API with the practice's own key, `claude-haiku-5-5` (the smallest current model, about $0.10 / $0.50 per million input / output tokens) at low effort, set in one Settings step. A larger model is tried only if the labelled tenders show extraction errors | Under Anthropic's [commercial terms](https://www.anthropic.com/legal/commercial-terms) and [data usage](https://code.claude.com/docs/en/data-usage) policy, API inputs are not used for training; only public notice text is sent. Extraction is a reading task, and the quote check catches invented values. Choose the model by measured agreement and cost per run | A larger model by default |
| 2026-11-04 | References count as comparable when the typology matches (housing types together, library with cultural, public space with landscape; schools and daycares apart) and the stated cost, area and age limits are met. When the notice asks for "comparable" references without a typology, code still checks the cost, area and age limits; if enough projects meet them, which ones count is left to the person and the tender can't be GO | A buyer asking for school references rarely accepts a daycare, and what counts as comparable is often a judgment. The grouping is one table in the fit-check code | Treating every education building as comparable |
| 2026-11-04 | A failed assessment is not retried automatically; at most 300 tenders are assessed per run (about $0.40 with Haiku) | A notice that always fails would otherwise cost money every day. The rest wait for the next run | Retrying until it works |
| 2026-11-04 | Output is one local Excel file (`output/Tenders.xlsx`), rebuilt every morning in place. Partner decisions typed into it are saved to Postgres first. If the file can't be read, the run stops instead of rebuilding it | A bid person already works in Excel; one file keeps one history of decisions. Postgres stays the source of truth, so the file can always be rebuilt | A new file every day (decisions scattered across files); Microsoft 365 Excel (needs an M365 account; documented as the option for practices that have one) |
| 2026-11-03 | Each setup runs its own n8n for this project only: in Docker (option A) or started with `start-n8n.bat` (option B, own data folder `n8n-data`, port 5680). Either way n8n may read and write files only in `output/` | A practice's tender data and credentials stay apart from any other automations on the same computer. n8n keeps credentials encrypted in its data folder, and workflows can't read environment variables, so no key is ever handled as plain text | Sharing one n8n with other projects; credentials in `.env` read by workflows |
| 2026-11-03 | A fetch that reaches the 40-page safety stop before TED's total stops with an error instead of saving part of the window | Found in a review of the error handling, before it ever happened: a partial window saved as a success would move the next window forward and skip the rest for good. The safety stop still caps one run at 40 requests | Saving the first 10,000 notices and continuing |
| 2026-11-03 | The fetch uses TED's Search API, not the website, with a 500 ms pause between pages (at most 40 requests per run) | TED's [legal notice](https://ted.europa.eu/en/legal-notice): notices "can be freely reused, for commercial or non-commercial purposes"; TED logos are not licensed. The Search API needs no key and lists no rate limit ([Search API](https://docs.ted.europa.eu/api/latest/search.html)); TED's [fair usage policy](https://ted.europa.eu/en/simap/developers-corner-for-reusers) allows 700 HTTP requests per minute and recommends the API for technical users. Personal data in notices is handled under GDPR (see 2026-10-25) | Scraping the TED website |
| 2026-11-03 | A fetch that gets 0 notices from TED stops with an error instead of saving an empty run | Zero notices for a whole catch-up window almost always means a change on TED's side. A failed run is retried from the same window next time; an empty "successful" run would move the window forward and skip those days for good. A false alarm costs one retry | Treating 0 notices as a normal quiet day |
| 2026-11-02 | The model only extracts requirements (with quotes); plain code compares them with the practice's references and facts and decides. New result *unresolved* when a requirement isn't stated in the notice. Each decision gets an *outcome* (won / lost / not submitted), and past outcomes on similar tenders are shown with new assessments. Reference projects are the main matching source; the practice profile holds only hard facts and preferences | Rules make the verdict repeatable and explainable; the model is used only where reading text is needed. A practice's real results are a better signal than a filled-in profile, and one column is enough to start collecting them | The model deciding go/no-go directly; a profile questionnaire as the main input |
| 2026-10-29 | Guardrails for AI coding assistants: deny rules for secrets files, ask before deleting data, bypass mode off, plus a PreToolUse hook that blocks commands naming `.env` or `.mcp.json` | Official Claude Code mechanisms ([permissions](https://code.claude.com/docs/en/permissions), [hooks](https://code.claude.com/docs/en/hooks)). The docs say deny rules cover Claude's file tools and recognised Bash commands but not every subprocess, so the hook adds a second layer; full isolation needs the sandbox | Relying on the assistant's good behaviour; a `.claudeignore` file (has no effect per the docs) |
| 2026-10-29 | TED notices are enough for v1 go/no-go | Checked on a real contract notice (TED 674275-2026, published 1 Oct 2026): the selection criteria section states the reference requirement (at least two comparable references from the last 5 years) and the required insurance cover. Award criteria and estimated value can be missing from the notice and sit in the buyer's documents (v2) | Downloading tender documents in v1 |
| 2026-10-29 | The fetch step keeps only calls for tenders and design contests (notice type `cn-*`) from the practice's countries; the rule step drops works contracts | A test query for CPV 71200000 since 1 Oct 2026 returned 2,911 notices EU-wide, including a works contract whose CPV list also contained design codes | Relying on the CPV code alone |
| 2026-10-29 | Two ways to run n8n: in this repo's Docker setup (recommended) or an n8n the practice already self-hosts, connected to Postgres on localhost:5432 | Many teams already run n8n; the workflow and database are the same either way, so the choice doesn't change the result | Making one n8n setup mandatory |
| 2026-10-29 | n8n runs in this repo's docker-compose (official image `docker.n8n.io/n8nio/n8n:2.45.6`, the current stable tag), on port 5679, localhost only, telemetry off | n8n 3.0 drops the npm install and is Docker-only; one `docker compose up` gives a reviewer the same setup; it stays separate from any other n8n on the machine. Licence: n8n Sustainable Use License allows free self-hosting for personal and internal use and building workflows a client runs internally; hosting n8n as a service where clients build their own workflows is not allowed ([licence FAQ](https://docs.n8n.io/n8n-community-license/community-license/license-faq)) | n8n Cloud (paid) |
| 2026-10-27 | Reframe from "tender radar" to an in-house go/no-go assistant that checks the practice's own references and learns from the partner's decisions | Finding and summarising tenders is widely available. The decision that costs a practice time is whether to bid, and that depends on its own references and judgment | Competing on coverage (more portals) |
| 2026-10-27 | Go/no-go criteria: eligibility (references, turnover, certificates), contract terms, execution risk, capacity fit; output GO / CONDITIONAL GO / NO-GO + max 3 open questions | Same structure as the construction go/no-go method described by KI-Syndikat (ki-syndikat.de, use case 06), where 2 of 3 required school references gives "conditional go" | Free-form summaries |
| 2026-10-27 | Every extracted requirement carries a quote from the notice | Traceability: a partner can check a claim in seconds | Trusting the model's paraphrase |
| 2026-10-27 | v1 reads the TED notice only; full tender documents (PDFs) are v2 | Notices are structured and free to reuse; documents sit on many buyer portals with their own terms. Whether notices carry enough selection criteria was checked on real data (see 2026-10-29) | Downloading documents from day 1 |
| 2026-10-25 | Viewing-only licence (all rights reserved) instead of MIT | The code is a demo of a service; others should not reuse or sell it without permission | MIT (allows commercial reuse) |
| 2026-10-25 | Contact persons in TED notices stay local, never committed | Notices can hold personal data; a public repo must not republish it | Committing raw sample notices |
| 2026-10-25 | State lives in Postgres, not in n8n | Idempotency, catch-up after downtime and an audit trail need a real database; the workflow stays simple and replaceable | Keeping state in n8n static data or a spreadsheet |
| 2026-10-25 | Pre-filter before any model call: CPV codes and publication date in the TED query, countries and notice type in the fetch step's plain code | Free and deterministic; fewer model calls means lower cost and fewer failure points | Sending every notice to a model |
| 2026-10-25 | Only 2 model steps (relevance, explanation; the explanation became the go/no-go assessment on 2026-10-27) | Chained probabilistic steps multiply failure; everything predictable is plain code | An agent deciding each step |
| 2026-10-25 | Relevance judge v1 = small Claude model; a cheaper judge is tested later on the same labelled set | Choose by measured agreement and cost per run, not by price per token | Picking the cheapest model untested |
| 2026-10-25 | Synthetic practice, public tender data | No client or employer data in a public repo | Real firm data |
